# Healthchecks backups to thoth

Destination: ZFS dataset `mercury/healthchecks-backup`, mounted at
`/mercury/healthchecks-backup`. Wash created it on 2026-10-10. The directory is
root-only mode 0700. Existing recursive Sanoid configuration covers this dataset;
replication to another machine has not been verified.

Thoth pulls at 04:00 America/New_York, with up to 15 minutes of random delay.
The persistent timer catches a missed run after boot. The newest 14 successful
archives are retained; `latest.tar.gz` points to the newest. Failed pulls do not
replace the latest archive or prune older backups.

## Contents and access

Each archive contains:

- `state/healthchecks.sqlite`: consistent online SQLite backup, including users,
  password hashes, checks, ping history, and notification integrations.
- Other local application state, excluding generated `static/` assets and live
  SQLite database journals. Static assets are regenerated by the NixOS service.
- `config/SECRET_KEY`: the matching Django secret.
- `config/settings.json`: effective Nix settings snapshot. Runtime paths are
  recorded as paths; the Django secret is stored separately above.
- Application version, deployed system store path, UTC backup time, and SHA-256
  hashes covering all archived state and configuration files.

The archive contains credentials and must remain private. Thoth verifies every
manifest hash, SQLite `quick_check`, and the presence of the secret and settings
before accepting it. The pull fails if the exact ZFS dataset is not mounted.

A dedicated generated Ed25519 key is encrypted in
`secrets/healthchecks_backup_ssh.age` for Wash and thoth. Its runtime file is mode
0400. The public half appears in `hosts/heimdall/healthchecks-backup.nix`.
Heimdall's `healthchecks-backup` account only accepts thoth's Tailscale IPv4,
forces the exporter command, and denies shells, PTYs, and forwarding. Its sudo
rule allows only that exporter without arguments. Heimdall's host key is pinned.
The existing TCP 31225 grant permits the pull; no policy change is needed.

The exporter uses SQLite's online backup operation and leaves Healthchecks
running. The pull's failure unit uses thoth's existing Slack `#alerts` helper.
This backup does not depend on Healthchecks receiving a ping about itself.

## Restoring

1. Extract the chosen archive into a private temporary directory. Validate
   `SHA256SUMS` and SQLite `integrity_check`. Use the recorded application version
   for the initial restore.
2. Review `config/settings.json` against the Nix configuration. Keep the matching
   `SECRET_KEY` available through the agenix secret; if it differs from the
   current key, re-encrypt the archived key into `healthchecks_secret_key.age`
   and deploy it. Editing only `/run/agenix` is not persistent.
3. Stop all three services explicitly: `healthchecks`, `healthchecks-sendalerts`,
   and `healthchecks-sendreports`. Stopping only the target may leave workers
   running. Preserve the current state directory for rollback.
4. Recreate `/var/lib/healthchecks` with owner/group `healthchecks`, mode 0750,
   and the archived `state/` contents. Set ownership recursively to
   `healthchecks:healthchecks`. The archive excludes live database journals;
   keep journals from the previous database out of the restored directory.
5. Start `healthchecks`; the service regenerates static assets. Check login,
   checks, schedules, ping URLs, and integrations. An older database may contain
   overdue checks and old notification credentials. After reviewing those,
   start `healthchecks-sendalerts` and `healthchecks-sendreports`.

Do not start alert workers during a disposable restore unless external delivery
is intentionally authorized.
