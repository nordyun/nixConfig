# Repository security and monitoring audit — 2026-09-10

This records the initial audit and subsequent remediation. Finding numbers match
the conversation. Severity describes the original finding, not necessarily its
current status. No secret values are included.

## Scope and limitations

- Reviewed repository configuration, docs/monitoring.md, recent monitoring commits,
  and relevant modules from the pinned Nixpkgs source.
- Ran targeted credential-pattern searches across 285 reachable Git commits.
  This was not an exhaustive secret-scanner or vulnerability-scanner assessment.
- Evaluated assertions and firewall settings for all four NixOS configurations;
  no failed assertions were found. Evaluation is not a runtime security test.
- Initial audit did not inspect live services, decrypted secrets, tailnet policies,
  Cloudflare settings, or GUI-managed monitoring rules. Later checks are recorded below.

## Security findings

### 1. High: Pushover credentials in Git history — application token closed

Commit `1672839` contains plaintext application-token and user-key assignments in
`hm/macbin/pushover.sh`. Later changes replaced them with secret-file reads.

Follow-up: the user reported rotating the credentials. A request to Pushover's
non-notifying validation endpoint returned `status: 0` and
`application token is invalid` for the historical pair. The historical application
token is therefore unusable; history rewriting offers little additional benefit
for that invalidated token. The historical user key's status was not independently
established. Current protected secret files could not be read for comparison.

### 2. High: unsupported Immich with security exception — upgrade/auth completed

`hosts/{anubis,thoth}/default.nix` enabled Immich 2.7.5 and explicitly permitted
the insecure package. The pinned package metadata listed CVE-2026-59258 and
CVE-2026-82272 and stated that the 2.x series was unsupported.

Completed:

- Both hosts now select Immich 3.1.0 from the existing unstable pin, including
  matching machine learning. Insecure-package exceptions were removed.
- Both host configurations evaluated; server and machine-learning packages fetched.
- User stopped Immich, paused mobile uploads, and backed up `/var/lib/immich`
  and `/var/lib/postgresql` before upgrading Anubis.
- User deployed and verified 3.1.0 through `photos.washatka.net`.
- Initial live checks showed local Immich healthy and public HTTP 502. User fixed
  the tunnel after correcting its origin following Anubis's LAN IP change.
- Google OAuth uses an Internal application in the family's managed Google
  organization. Three existing accounts were linked and login/mobile uploads tested.
- `modules/immich-oauth.nix` uses an Agenix client secret, disables automatic
  registration, and preserves `server.publicUsers = false`, the public URL, and
  storage template `{{y}}/{{MM}}/{{filename}}`.
- User deployed and confirmed password login disabled. Existing sessions are not
  necessarily revoked by that setting. File-based system settings are authoritative.

Remaining: port 2283 still listens on all IPv4 interfaces and is globally allowed
by Anubis's firewall. The working connector is on Neptune. Restricting origin
access to Neptune was discussed but NOT implemented. No Cloudflare Access gate
was configured as part of this work.

Clarification: a globally opened host port is not automatically Internet-reachable
behind Neptune. Direct Internet exposure depends on forwarding, routing and IPv6.
Immich remains publicly reachable through Cloudflare; origin restrictions reduce
lateral access and filtering bypass, not the application's public API exposure.

Thoth migration: comments require separate appropriately tuned ZFS datasets for
managed media and PostgreSQL, correct mount/ownership handling, write durability,
and offsite backups. Existing mercury external-library backups do not alone cover
these directories. Anubis uses PostgreSQL 15; Thoth defaults to 17. Use a planned
dump/restore or align major versions; do not copy a PG15 data directory into PG17.
Add Thoth's host key to OAuth-secret recipients and import the shared OAuth module
when migrating. A NixOS rollback alone does not reverse database migrations.

### 3. High: broad trust of Tailscale peers — in progress. Waiting for thoth and zfs backup

All four hosts declare `networking.firewall.trustedInterfaces = [ "tailscale0" ]`.
Per-interface port allowances therefore do not establish least-privilege access.
Follow-up: the user supplied the active policy. Its grants contain
`{"src":["*"],"dst":["*"],"ip":["*"]}`, confirming allow-all tailnet access.
Its separate Tailscale SSH policy allows members to access their own devices in
check mode. That SSH policy does not configure ordinary OpenSSH on port 31225.
The supplied active rules are saved in `tailscale-policy-before.hujson` as a
reference for this migration, not as a recommended final policy.

Start by inspecting the tailnet policy and defining identity/service access using
Tailscale grants. Preserve administrative access, monitoring, NUT, and Neptune's
exit-node use. Do not simply remove interface trust and assume the result works:
Tailscale's default netfilter mode can install its own input acceptance rules.
Any host-firewall hardening must account for those rules and global service ports.

### 4. Medium: shared Monit control credentials — done

`modules/monit.nix` documents a shared collector/agent-control password across
hosts. Compromise of one credential can expose configured service control on other
reachable agents. Separate collector submission from agent-control credentials,
use distinct credentials, and restrict agent access to the collector. HTTP inside
Tailscale is carried over its encrypted transport, not plaintext on the LAN.

Repository remediation: the NixOS agents now use a submission-only secret and
unique control secrets for Horus, Anubis, and Neptune. Each control secret is
encrypted only to wash and its corresponding host. Monit's HTTP source allowlist
requires localhost or Horus (`100.86.167.115`) in addition to password
authentication, independently of Tailscale's broad interface trust. Remote
control is preserved; agents register their new credentials with M/Monit.
The existing collector submission login and endpoint are preserved.

All three replacement secret configurations passed `monit -t`; targeted Nix
evaluation passed all four hosts' assertions and confirmed the new secret
declarations on the three collector agents. The user confirmed full deployment
on 2026-09-11, including the Ubuntu migration discussed alongside this change.
Closure is based on that confirmation; live access checks were not independently
repeated. Horus remains a trusted control point. The obsolete combined secret
can be retired once no deployment references it. See
[migration and verification steps](monit-credential-migration.md).

### 5. High: WayVNC without authentication — stopped; removal pending deployment

`hosts/anubis/systemdservices.nix` starts WayVNC on `0.0.0.0`. No authentication
configuration was found in the repo. An unmanaged user config may provide it;
the deployed service was not verified unauthenticated. Declare authentication or
restrict access via binding/tunneling and tailnet policy.

Live follow-up (2026-09-11): wash's user service is in an automatic restart loop,
logging `No such output` for the configured `HDMI-A-1`; no TCP listener on 5900
was present during the check. `/home/wash/.config/wayvnc/config` was absent.
This does not establish safe behavior once the output is available. Confirm
whether desktop access is still needed before removing the service or configuring
authenticated access/a loopback listener with SSH forwarding.

After the user reinserted the display dongle, the service became active and a
live socket check confirmed `0.0.0.0:5900`. The user reached it over Anubis's
Tailscale IP and reported a password prompt followed by unsuccessful login.
The available journal records `Client handshake timed out`, not an explicit
bad-password error. Authentication remains unverified; a client prompt alone
does not establish the server's configured authentication method.

A subsequent local RFB handshake returned protocol 3.8 and offered only security
type 1 (None), confirming the running server offers no authentication. The
client was macOS Screen Sharing; its password prompt did not reflect an enabled
WayVNC password. No desktop session was opened by this diagnostic. Configure
authentication compatible with that client and restrict network access, or bind
to loopback and require an authenticated tunnel before closing this finding.

The user chose to retire screen sharing. Stopped `wayvnc.service` through wash's
user systemd manager and verified it was inactive on 2026-09-11. The user is
removing its repository configuration; deploy that removal so a later graphical
session or reboot cannot start the old service again.

### 6. Medium: Slack webhook in process arguments — fixed in configuration; deployment pending

`modules/notify.nix` passes the decrypted webhook URL as curl's argument. Local
process inspection can expose it depending on `/proc` access controls. Use stdin
or a protected curl configuration file rather than secret-bearing arguments.

Remediation: `notify` now supplies the URL using Bash's builtin `printf` piped
to `curl --config -`. The URL is not passed in process arguments or exported
environment variables. Malformed secrets containing whitespace, quotes or
backslashes are rejected without printing their contents. Message formatting,
timeouts, retries and the existing graceful delivery-failure behavior are retained.

A local HTTP test with a synthetic webhook verified the JSON POST and inspected
the live curl process arguments to confirm URL absence. Empty/malformed-secret
checks, Bash syntax validation, and the Nix package build (including ShellCheck)
passed. No Slack messages were sent. Deploy
the updated `notify` package on hosts importing `modules/notify.nix`.

## Implementation and reliability findings

### 7. High: backup scripts have broken failure handling — open

Active `hosts/{anubis,thoth}/rcloneOnedrive.sh` files contain literal Nix expressions
inside standalone shell files; these are not interpolated and cause bad shell
substitutions. Notification success controls failure exit behavior, intermediate
errors can be ignored, and a final success exit can hide failures. Flattening
directories with `cp -n` can silently skip duplicate basenames.

Fix failure propagation independently of notification delivery before adding
Healthchecks. The alternate `onedrivePhotoSync.sh` is not wired into the service
and has a separate `set -e` problem: `((count++))` returns failure at zero.

### 8. High: persistent storage not covered by baseline Monit — open

`modules/monit.nix` checks only `/`; Anubis uses tmpfs there. Add capacity checks
for persistent filesystems and mercury, ZFS health alerts, and remote SMART alerts.
Current SMART wall notifications are easy to miss. LibreNMS GUI rules were not
available to establish whether they supplement these gaps.

### 9. High: no declared independent site/collector alarm — open

Horus separates monitoring from other hosts but shares local infrastructure.
Add an externally hosted heartbeat for Horus/site connectivity and central
missing-agent alerts. Local Slack notifications cannot report a dead host.
The monitoring document says M/Monit central alerting is unused.

### 10. Medium: UPS shutdown depends on Tailscale — open

Neptune's NUT client uses Horus's tailnet address. This removes DNS dependence,
not overlay dependence. NUT's lost-communication handling depends on the last
known power state; last-known-on-battery is different from last-known-online.
Consider a stable source-restricted LAN path for local clients and validate failure
cases during controlled maintenance, not an unplanned real shutdown test.

### 11. Medium: notifications can be lost permanently — open

`notify` retries briefly and returns success after delivery failure. Monit exec
actions normally run once per failure transition; no durable Slack queue exists.
Add durable retries or controlled reminders and explicit recovery notifications.
Monit's event queue does not queue arbitrary failed curl invocations.

### 12. Medium: partial Tailscale Serve configuration after failure — open

`modules/tailscale-serve.nix` waits about a minute, resets mounts, and adds them
sequentially without restart-on-failure. A failure can leave partial configuration.
Add recovery/retry behavior. An unchanged active oneshot does not necessarily
rerun on every rebuild, contrary to the monitoring document's broad statement.

## Efficiency and overlap

| Component | Assessment |
|---|---|
| ntopng + Redis | Strongest removal candidate if unused. Enabled on Anubis/Thoth by modules/server/default.nix, outside the documented monitoring stack. |
| Monit | Useful local recovery and checks. Prefer systemd for ordinary daemon crash restarts; use Monit where it adds meaningful health checks. |
| M/Monit | Optional collector/control UI; assess value while central alerting is unused. Adds state and a license dependency. |
| LibreNMS | Useful for switch/interface/SNMP history; assign it ownership of network alerts. |
| Uptime Kuma | Useful protocol/application checks that process existence cannot replace. |
| Healthchecks | Useful once jobs send meaningful completion/failure pings; no backup integration was declared. |
| Homepage | Four links could be served statically if reducing maintenance matters. |

Keep local tailscaled monitoring: it can recover a dead daemon while the collector
cannot reach that host. Slack may still work over ordinary Internet access.
Process existence alone does not establish overlay connectivity.

Do not tune LibreNMS's eight poller threads without measuring poll duration, CPU,
memory and disk latency. Redundant alert ownership matters more than tool count.

## Other observations — open unless stated otherwise

- No declared backups for GUI-managed state in M/Monit, LibreNMS, Kuma and
  Healthchecks. Rebuilding services is not restoring their databases/configuration.
- Syncoid is enabled but its replication command blocks are commented out on
  both storage hosts; enabling it alone does not establish replication.
- Homepage is documented as loopback-only, but the repo and pinned module do
  not explicitly set its listener address. Verify and configure the bind.
- Router quarantine blocks forwarding between two named IPv4 interfaces rather
  than defining a default-deny VLAN boundary. Global UDP allowances still apply.
  IPv6 `wan` sysctls do not match the configured `enp1s0` name.
- n8n is unpinned; Letta uses latest with automatic updates, weakening reproducible
  deployment and rollback confidence.
- M/Monit uses a dedicated user but executes writable program files and has
  minimal unit sandboxing relative to several upstream NixOS services.
